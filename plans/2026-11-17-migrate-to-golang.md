# План миграции telegram-mcp на Go

Статус: **миграция завершена и принята владельцем**. После проверки auth/import/QR владелец повторно подтвердил работу подключённого Go MCP («проверил, все работает»). Python/secretary/Business и старые инструкции удалены из репозитория; реальные секреты, пользовательские данные и конфигурация MCP-клиента не изменялись агентом. Инструкция: [README](../README.md), [подробный контракт](../docs/go-migration.md); доказательства и ограничения: [отчёт](2026-11-17-migrate-to-golang-progress.md).

Первоначальный план проекта: [2026-09-10-initial-project.md](2026-09-10-initial-project.md). Результаты проверки прежнего объёма: [2026-11-17-migrate-to-golang-verification.md](2026-11-17-migrate-to-golang-verification.md). При расхождении приоритет имеет этот документ с уточнениями владельца.

## 1. Цель и границы

Единственный текущий пользователь — владелец проекта. Цель:

> Локально собрать Go-версию, использовать уже сохранённые Telegram credentials и сессию либо войти по QR с облачным паролем, подключить MCP к своему клиенту. Для запуска собранной программы не нужны Python, uv и qrencode. Автоматизация и распространение бинарников — отдельная последующая работа.

**Язык — Go.** Кандидаты: официальный Go MCP SDK и `gotd/td` для пользовательского MTProto. Версии закрепить после технической проверки, не использовать плавающие зависимости.

### Входит в перенос

- Один бинарник `telegram-mcp`, stdio MCP; целевая платформа миграции — macOS владельца.
- Чтение диалогов, истории, поиск, получение сообщения по ссылке, скачивание медиа.
- Прямая отправка через пользовательский аккаунт: allowlist, маркер агента, форматирование и ответы.
- Использование существующих API credentials и, по возможности, Telethon StringSession.
- Встроенный QR-вход с поддержкой облачного пароля Telegram (2FA).
- Настройка и диагностика без раскрытия секретов, локальная сборка и проверки вручную.

### Не входит

- **Secretary, Business-доставка, Bot API, Anthropic, polling, права бота и systemd-служба secretary.** Если такая функциональность понадобится, это отдельный бот и отдельный проект, не следующий этап этого MCP.
- Строгая обратная совместимость схем и текстовых результатов Python-версии.
- Автоматизированный откат приложения, параллельная поддержка двух реализаций и миграция state secretary.
- Linux и Windows: поддержка, сборки и проверка хранения секретов на этих ОС сейчас не нужны.
- HTTP MCP, собственный updater, плагины и собственная реализация MTProto.
- **CI/CD и бинарная поставка:** workflows, автоматизация сборок/проверок/релизов, GitHub Releases, release-матрица, checksums, подпись/notarization, упаковка и Brew tap. Вернуться к ним после миграции.
- Развитый CLI редактирования конфигурации — возможное последующее удобство, не условие завершения миграции.

Изменять интерфейсы и поведение допустимо. Это не отменяет allowlist, защиты секретов, ограничений чтения и предсказуемости отправки.

## 2. Что сохраняем из текущего проекта

Прежняя Python-реализация (исходная ревизия `e6391b2`) была источником рабочих сценариев, а не побайтовым эталоном для Go. После приёмки она удалена.

| Область | Решение |
|---|---|
| Семь MCP-инструментов | Сохранить сценарии; имена `tg_me`, `tg_dialogs`, `tg_history`, `tg_search`, `tg_message`, `tg_send`, `tg_download` разумно оставить для удобства |
| Формат результатов | Компактный текст; допустимо изменить детали, если ссылки, ID, авторство и порядок понятны |
| Отправка | Только MTProto от пользовательского аккаунта, без Business-атрибуции `via_business_bot_id` |
| Allowlist | Проверять до подключения и получения credentials; оставить `TELEGRAM_MCP_SEND_ALLOWLIST`, default для новой версии — `me`; канал добавляется явно |
| Маркер | Сохранить `TELEGRAM_MCP_AGENT_MARKER`, default `🤖`; пустое значение не отключает маркировку; broadcast-посты без маркера |
| Недоверенный контент | Сохранить ограждение `untrusted-telegram-content` и экранирование вложенных тегов/атрибутов; не считать это полной защитой от prompt injection |
| Markdown/HTML | Выбрать и документировать поддерживаемый диалект; буквальная совместимость с Telethon не обязательна |
| FloodWait | Возвращать понятную ошибку с временем ожидания, не пережидать ограничение незаметно для MCP-клиента |

**Изменение доставки должно быть явным:** старые bot credentials не включают Business-режим в Go. `doctor` и инструкция сообщают, что сообщения отправляются напрямую от аккаунта. Старые записи бота не удалять и не использовать. Это выбранная архитектура, а не fallback после ошибки Bot API.

### Проверенная исходная база

При верификации кода `e6391b2`:

- `uv run --frozen --offline pytest -q`: **139 passed**.
- `uv run --frozen --offline ruff check` и `ruff format --check`: успешно.
- Реальный stdio `initialize` → `tools/list`: все семь инструментов.

Часть этих тестов относится к удаляемой функциональности. Сохранять их количество или переносить тесты secretary/Business не требуется.

## 3. Существующие секреты — приоритет совместимости

Желательно обойтись без повторного ввода API credentials и без нового входа при наличии рабочей сессии. Это отдельное требование, несмотря на допустимость остальных breaking changes.

### Имена и порядок чтения

Сохранить текущие имена:

| Назначение | macOS Keychain service | Environment |
|---|---|---|
| API ID | `telegram-mcp-api-id` | `TELEGRAM_MCP_API_ID` |
| API hash | `telegram-mcp-api-hash` | `TELEGRAM_MCP_API_HASH` |
| Старая Telethon StringSession | `telegram-mcp-session` | `TELEGRAM_MCP_SESSION` |

Для старых записей сохранить текущий Keychain account на основе `$USER` и приоритет **Keychain → env**, как в `config.py` исходной ревизии. Отсутствующее/недоступное значение может читаться из env; найденное, но некорректное значение диагностировать, а не молча подменять другим источником.

Для первой версии достаточно существующих env-настроек поведения. Файл настроек и `config set` не нужны до появления конкретной необходимости: так не возникает дополнительного неясного приоритета источников.

### Импорт сессии

У `gotd/td` есть `session.TelethonSession()` — использовать его как кандидата для импорта, не писать собственный декодер без необходимости. Наличие декодера ещё не доказывает успешный запуск с импортированной сессией: в StringSession отсутствуют `tg.Config` и server salt.

Предлагаемый порядок:

1. Если есть собственная Go-сессия, использовать её.
2. Если её нет, попробовать импорт существующей Telethon StringSession из прежних источников.
3. Проверить авторизацию и сохранить рабочее состояние в **отдельной записи macOS Keychain для Go-сессии**. Не сохранять Go-формат под старым `telegram-mcp-session` и не менять смысл `TELEGRAM_MCP_SESSION`.
4. При повреждении/отзыве сессии вернуть понятную диагностику и предложить интерактивный QR-вход. В `serve` не запускать вход автоматически.

Конкретное имя Go-записи закрепить на этапе прототипа. Явную команду импорта добавить только если автоматический импорт при отсутствии Go-сессии окажется неудобным или неоднозначным.

**Не удалять и не перезаписывать старую сессию.** Это недорогая защита действующего доступа, а не обязательство поддерживать полноценный rollback. Не запускать Python и Go одновременно с одним импортированным auth key до проверки допустимости такого использования; для первого переключения остановить Python MCP.

### Хранение и защита секретов на macOS

В этой миграции поддерживается только macOS. API credentials и сессия хранятся в **macOS Keychain**; существующие env-переменные остаются дополнительным источником чтения по правилам выше. Хранилища для Linux и серверов без графического окружения сейчас не проектируем.

- Новую Go-сессию сохранять в отдельной записи Keychain, не изменяя старую Telethon-сессию.
- Если Keychain недоступен для чтения, использовать явно заданные env-переменные там, где они предусмотрены. Если значения нет и там — сообщить, какой секрет недоступен, без раскрытия его содержимого.
- Если запись в Keychain не удалась, сообщить об ошибке сохранения. **Не записывать сессию в файл вместо Keychain автоматически** и не объявлять вход/импорт успешно завершённым.
- Сохранять новую сессию атомарно и только после успешной авторизации. При отмене входа или ошибке оставлять прежнюю рабочую Go-сессию нетронутой.
- Секреты, session strings, QR login URL и облачный пароль не должны попадать в логи, аргументы процессов, диагностический вывод и тестовые данные. QR показывается только в интерактивном терминале, пароль вводится без отображения.
- Выбрать способ записи в Keychain без передачи секрета в аргументах процесса; вызов `security ... -w <secret>` не использовать.

Приёмка — локальные сборка, вход, сохранение сессии и повторный запуск на Mac владельца.

## 4. QR + облачный пароль — обязательный сценарий

QR-вход — основной путь восстановления/создания сессии: доставка кодов ранее работала ненадёжно. Отлаживать отправку кодов как условие готовности первой версии не нужно.

**QR не отменяет облачный пароль.** После подтверждения на уже авторизованном телефоне библиотека должна корректно обработать требование 2FA и запросить пароль в терминале без отображения ввода.

Требования реализованы и покрыты offline-тестами; основной реальный auth/restart принят владельцем. Отдельного live-протокола для каждого QR edge case и второго аккаунта в диалоге нет — чекбоксы ниже не означают, что агент входил в Telegram или наблюдал каждый сценарий:

- [x] QR генерируется внутри бинарника, внешний `qrencode` не требуется.
- [x] Вход не зависит от успешной доставки кода по телефону/в Telegram.
- [x] Просроченный QR обновляется, подтверждение обрабатывается без гонки регистрации обработчика.
- [x] Поддерживаются аккаунты с облачным паролем и без него.
- [x] Неверный облачный пароль даёт понятную ошибку и возможность повторить ввод либо отменить вход.
- [x] Ctrl+C отменяет процесс, старая рабочая сессия остаётся нетронутой.
- [x] Без интерактивного терминала вход завершается с объяснением; QR и login URL не уходят в перенаправленные логи.
- [x] После успешного входа сессия сохраняется и работает при повторном запуске без QR/пароля.

В gotd есть пример QR/2FA, но его нельзя копировать буквально: проверенный пример выводит login URL и читает пароль обычной строкой. Пользователь вводит облачный пароль самостоятельно; агент не получает пароль, QR-токен или содержимое сессии.

Вход по коду можно оставить дополнительной возможностью, если он не усложняет основной сценарий. Он не блокирует завершение миграции.

## 5. Минимальный интерфейс и организация

Реализованные команды:

```bash
telegram-mcp init              # API credentials, только если их ещё нет
telegram-mcp auth login --qr   # новый вход / замена Go-сессии после успешной авторизации
telegram-mcp doctor            # состояние и источники настроек, без значений секретов
telegram-mcp serve             # только stdio MCP, без интерактивных вопросов
```

`doctor` различает отсутствие credentials, недоступное хранилище, ошибку импорта и необходимость нового входа. Только явный `doctor --network` проверяет авторизацию в Telegram; обычный `doctor` работает локально.

Пример структуры, не требование создать все пакеты заранее:

```text
cmd/telegram-mcp/       CLI и запуск
internal/config/        env-настройки и валидация
internal/credentials/   существующие секреты, хранение и импорт сессии
internal/telegram/      MTProto, auth, разрешение peers, чтение и отправка
internal/render/        компактный вывод, маркер и форматирование
internal/mcpserver/     MCP-инструменты
```

Отдельные процессы, `internal/business`, `internal/secretary` и Anthropic-зависимости не нужны.

## 7. Итог решений и прежние оценки

Миграция личной установки завершена; подтверждённой календарной оценки нового объёма не составлялось. Прежние **20–35 дней / 4–7 недель**, **10–18 дней** и 2–3 дня прототипа не являются фактической длительностью или обещанием дальнейшей работы.

1. Go-сессия: `telegram-mcp-go-session`, нативный Security.framework через `keybase/go-keychain`/cgo; без секретов в argv.
2. Форматирование: CommonMark и HTML gotd, без Telethon-совместимого адаптера.
3. Отправка: прямая пользовательская MTProto, default allowlist `me`; secretary/Business не входят в проект.
4. Старые секреты и пользовательские данные сохранены. Исторические планы/верификация оставлены как архив, их Python-пути относятся к исходной ревизии.

CI/CD, бинарная поставка, другие ОС и публичный релиз остаются отдельной будущей работой, не незавершёнными условиями этой миграции. Текущие ограничения реализации перечислены в отчёте и руководстве.
