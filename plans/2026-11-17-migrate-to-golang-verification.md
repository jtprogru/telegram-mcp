## Вердикт для предыдущей редакции

**План подходит для запуска технического прототипа, но пока не готов как исполнимый план полного переноса.** Выбор Go обоснован, разделение MCP/secretary и последовательность «бинарники → Brew» стоит сохранить. Блокирующих оснований отказываться от Go не обнаружено; работоспособность Go-реализации ещё не доказана.

Перед полным переносом нужны: контракт совместимости, решение по существующей сессии и откату, проверка диалекта форматирования и Business-доставки, выбранная схема хранения секретов. Перед переносом secretary — отдельное решение по подтверждению updates и неопределённым результатам действий.

Ошибка масштаба плана — **недостаточная детализация сложных мест**: «сохранить внешнее поведение» и «определить поведение при повторах» скрывают существенно больше работы, чем структура каталогов. Каталоги при этом правильно обозначены как ориентир, а не обязательная архитектура.

## 2. Замечания к плану

Приоритеты: **P1** — закрыть до соответствующего этапа реализации; **P2** — явно включить в условия готовности; **P3** — редакционная правка.

### V1 · P1 · Контракт совместимости должен предшествовать реализации

**План:** строки 210–216, этап 2. **Основание:** `src/telegram_mcp/tools.py:109–319`, `tests/test_tools.py`, `tests/test_formatting.py`.

«Сохранить семь инструментов» недостаточно для сохранения API. Сейчас проверяются имена инструментов, схема `reply_to`, отдельные helpers, форматирование и отправка, но нет полноценного поведенческого покрытия `tg_history`, `tg_search`, `tg_dialogs`, `tg_message`, `tg_download`.

Различия Python/Go SDK могут затронуть omitted/null/default, входные схемы, формат результата и ошибки. Различия Telegram-библиотек — порядок выдачи, границы `min_id/max_id/since/until`, получение `access_hash` после перезапуска, лимиты и пагинацию. Перенос существующих тестов сам по себе этого не проверит.

**Изменение:** до реализации сохранить эталон `tools/list` и language-neutral fixtures. Проверять входную семантику, текстовый MCP-результат и `isError`, ограничения и сортировку, авторство/пересылки/ссылки, пустые результаты, скачивание и ошибки. Сохранить `untrusted-telegram-content`, обезвреживание вложенного fence и безопасные атрибуты из `formatting.py:190`, а не только allowlist и маркер. Эта разметка — сигнал недоверенного содержимого, не абсолютная защита от prompt injection.

Преднамеренные изменения — default allowlist `me`, исправление FloodWait и ошибок secretary — перечислить отдельно: нельзя одновременно обещать буквальную совместимость и незаметно менять их.

**Приёмка:** Python и Go проходят общий набор fixtures; все допустимые отличия записаны явно.

### V2 · P1 · Совместимость Markdown не обеспечивается штатным парсером gotd

**План:** строки 198–204 и 214. **Основание:** `src/telegram_mcp/botapi.py:85`, официальный `telegram/message/markdown/markdown.go` в gotd.

Текущий код использует диалект Telethon, а проверенный парсер gotd заявляет CommonMark. Уже есть конкретные различия:

| Вход | Текущий Telethon, проверено локально | gotd, по документации исходного кода |
|---|---|---|
| `*text*` | Буквальные звёздочки, без entities | Italic |
| `__text__` | Italic | Bold |

Правильные UTF-16 offsets не исправляют неправильный выбор entity. Поиск библиотеки или адаптер совместимости может оказаться заметной частью переноса.

**Изменение:** вынести выбор парсера в технический прототип; проверить один и тот же текст через MTProto и Bot API. Зафиксировать fixtures для обоих примеров выше, HTML, code blocks, ссылок, emoji перед форматированием, маркера и `reply_to`. Совместимый адаптер предпочтительнее молчаливого перехода на CommonMark; иной выбор требует явного изменения контракта.

**Приёмка:** совпадают plain text, типы entities и их UTF-16 offsets, а не только визуально похожее сообщение.

### V3 · P1 · Не определены переход существующей установки и откат

**План:** строка 150, этапы 2–3. **Основание:** `src/telegram_mcp/config.py:18–35,68`, существующая StringSession и MCP-команда из README.

Импорт упомянут лишь как фактор увеличения оценки. Не решено, должен ли текущий пользователь повторно входить, какие имена Keychain/env сохраняются и где находится новая сессия. Перезапись `telegram-mcp-session` в Go-формате может сломать Python при откате. Переход к `telegram-mcp serve` также меняет команду запуска MCP-клиента.

**Изменение:** до полного переноса выбрать один основной путь: повторный вход либо явный импорт через существующий декодер gotd. Хранить Go-сессию отдельно от Python-сессии; не перезаписывать и не удалять старую автоматически. Зафиксировать versioned state, атомарное сохранение, поведение при повреждении данных и политику одновременных запусков. Для импортированного auth key отдельно проверить ограничения его совместного использования; не обещать безопасный параллельный запуск без теста.

Описать переключение MCP-команды, проверку новой установки и возврат к прежней. На этапе бинарного MCP Python-secretary продолжает работать; переключать его следует отдельной операцией, не запуская два poller одного бота.

**Приёмка:** пройден путь «работающий Python → Go → откат» без потери старых credentials и без одновременной обработки updates.

### V4 · P1 для secretary · Нужна политика не только дублей, но и пропуска обработки

**План:** строки 95–99 и этап 4. **Основание:** `src/telegram_mcp/secretary.py:155–161`, `src/telegram_mcp/agent.py:316`.

Риск дублей после отправки описан правильно. Дополнительно offset повышается **до** `dispatch`; исключение логируется, но offset после пачки сохраняется. Локальная проверка подтвердила: неуспешный `update_id=42` записывается как `offset=43`. Следующий `getUpdates` с этим offset подтвердит update без повторной обработки.

Просто сохранять offset после каждого update недостаточно. Между внешним действием и записью состояния остаётся окно сбоя; ответ с потерянным HTTP-response нельзя автоматически считать неотправленным. Один запуск модели также может выполнить несколько действий до ошибки.

**Изменение:** до реализации secretary определить состояния обработки и судьбу каждого случая: успех, ошибка до внешнего действия, частичный успех, неизвестный результат, restart, повреждение state. Выбрать политику повторов и хранения результатов; необратимые действия не повторять автоматически при неизвестном исходе. Не обещать exactly-once без механизма, который действительно обеспечивает это на стороне внешних действий.

Сохранить лимит итераций runner, привязку reply к исходному чату, проверку прав и локальный запрет необратимых операций. Обработать выключенную connection и обновление прав. Историю обрезать один раз по целым turns с сохранением всех пар tool use/result; тестировать путь через `agent.handle`, а не только `trim_history` отдельно.

**Приёмка:** fault-injection тесты до/после внешнего действия и сохранения state, повтор одного update, повреждённый state, неизвестный исход; отсутствуют необъяснённые повторы и пропуски.

### V5 · P2 · Business setup и доставка отсутствуют в явном gate прототипа

**План:** этап 1 и предлагаемый CLI. **Основание:** `scripts/connect_bot.py:42–63`, `src/telegram_mcp/tools.py:282–293`, `src/telegram_mcp/botapi.py:108–133`.

Business-доставка включена в объём первого релиза, но проверка этапа 1 не разделяет отправку через аккаунт и через бота. В примерах CLI не видно замены `make bot-connect`. Discovery через `getUpdates` конфликтует с работающим secretary; это не обычное чтение конфигурации.

**Изменение:** включить в прототип обе доставки, запрет fallback после ошибки бота, отсутствующий reply target и неполную конфигурацию. Предусмотреть в CLI операцию подключения Business-бота, проверку connection и понятную диагностику конфликтующего polling/webhook. Не выключать чужой webhook и не запускать второй poller автоматически.

**Приёмка:** новый пользователь подключает Business-бота без репозитория; ошибка Bot API не вызывает прямую отправку через аккаунт.

### V6 · P2 · Хранение секретов и «один бинарник» пока не имеют проверяемого контракта

**План:** строки 61–63, 135 и этап 3. **Основание:** `src/telegram_mcp/config.py:68`, `deploy/telegram-secretary.service`.

План верно требует выбора хранилища, но не делает это выходным артефактом раннего этапа. Нужны приоритеты конфигурации: сейчас Keychain имеет приоритет над env, а появление `config set` добавит ещё один источник. Без этого команда настройки может записывать значение, которое не используется.

«macOS/Linux» не задаёт архитектуры, минимальные версии и зависимости secret backend. Pure Go MTProto не доказывает автономность всей сборки: выбранный backend может требовать cgo, системный сервис или внешнюю утилиту.

**Изменение:** зафиксировать матрицу ОС/архитектур, backend для desktop и явный headless-режим, порядок источников, права файлов при их использовании, маскирование ошибок и отсутствие секретов в argv/логах. Сохранять старую сессию до успешного входа; QR и 2FA показывать/вводить только в интерактивном терминале. Не копировать QR-пример библиотеки буквально: он выводит login URL и читает пароль обычной строкой.

`doctor` должен показывать источники и готовность без значений секретов; `serve` не должен запускать интерактивный вход. stdout принадлежит только MCP. Для завершения проверить EOF, SIGTERM, отмену запросов и освобождение session lock. У secretary должны быть только необходимые секреты, включая Anthropic API key, но не MTProto-сессия.

**Приёмка:** установка, login, restart, update и rollback на чистых поддерживаемых системах, включая headless; все необходимые системные предпосылки перечислены.

### V7 · P2 · CI и gate оценки нужно перенести раньше

**План:** строка 206 и этап 3.

«Без большого самописного слоя» не даёт однозначного решения о продолжении. Настройка CI после переноса откладывает обратную связь по контрактам и платформам.

Сетевые интеграционные тесты — только отдельным явным запуском. По окончании прототипа представить таблицу сценариев, ограничений, недостающих адаптеров и новую оценку. Решение go/no-go принимается по этой таблице, а не по субъективному размеру слоя.

Сроки **10–18 / 20–35 дней** не опровергнуты, но и не верифицированы: нет пробного переноса и оценки адаптера форматирования, storage и recovery secretary. Сохранить их как предварительный диапазон, не как критерий приёмки.

## 3. Уточнённый порядок работ

Этот вариант сохраняет направление исходного плана, но добавляет измеримые выходы. Это предложение, не начатая реализация.

### Этап 0. Зафиксировать контракт и решения о переходе

- Зафиксировать Python baseline, схемы семи инструментов и fixtures, расширив покрытие read-инструментов.
- Отдельно описать намеренные изменения: default `me`, политика FloodWait, исправления secretary.
- Выбрать ОС/архитектуры, storage/backend, приоритеты конфигурации, путь миграции сессии и откат.
- Определить замену команд setup, login и bot-connect; выбрать точные версии Go и зависимостей.

**Выход:** проверяемая матрица совместимости, список допущений и инструкция перехода; секретов в fixtures нет.

### Этап 1. Вертикальный прототип Go с минимальным CI

- Вход по коду и QR/2FA, безопасное сохранение и повторный запуск; импорт — только если выбран.
- Saved Messages, приватный канал по ID после restart, history и оба вида поиска с пагинацией.
- Совместимость Markdown/HTML/entities, прямой и Business-send, replies и запрет fallback.
- Скачивание медиа, отмена запроса, отключение и восстановление соединения.
- Проверка выбранного secret backend и сборки/запуска на целевых системах.

**Выход:** результаты каждого сценария, известные ограничения, нужные адаптеры, закреплённые зависимости и пересмотренная оценка. При критических провалах не начинать полный перенос; рассмотреть другой подход, включая самодостаточную Python-поставку.

### Этап 2. Перенести MCP и полный setup

- Реализовать CLI, credentials и семь инструментов в рамках согласованного контракта.
- Централизовать allowlist, маркер, маршрутизацию отправки и запрет небезопасного fallback.
- Проверить схемы и ответы через реальный stdio, отсутствие секретов в диагностике, EOF/SIGTERM.
- Прогнать контрактные fixtures и отдельные разрешённые интеграционные сценарии.

**Выход:** все обязательные проверки зелёные; отличия от Python только согласованные. Python-secretary пока не переносится.

### Этап 3. Выпустить MCP-бинарники и проверить переключение

- Добавить выбранную владельцем лицензию, release workflow, checksums, version/build metadata и инструкцию проверки артефакта.
- Определить способ доверенной доставки/checksum; для macOS проверить реальную загрузку и запуск с учётом quarantine/Gatekeeper. Если нужны подпись/notarization — оформить отдельным решением, не считать их уже выполненными.
- Проверить установку без Python/uv/Makefile/checkout/qrencode, настройку Business и регистрацию MCP.
- Проверить обновление и откат к прежней установке; не удалять её до принятия нового релиза.

**Выход:** коллега проходит весь сценарий на чистой поддерживаемой системе по опубликованной инструкции.

### Этап 4. Спроектировать и перенести secretary

- До кода утвердить политику обработки updates и неизвестных исходов действий.
- Проверить совместимость Anthropic runner: лимит итераций, ошибки, история, динамические права и отсутствие повторного выполнения одного tool call при сборке истории.
- Реализовать state/recovery, целостную обрезку истории, ограничения действий и согласованную модель конкурентности.
- Адаптировать systemd, изоляцию секретов и атомарное переключение единственного poller; определить совместимость offset/state при откате.

**Выход:** пройдены fault-injection тесты, проверен systemd restart и безопасное переключение с Python-secretary.

### Этап 5. Brew tap

Только после успешной бинарной установки и обновления. Brew автоматизирует уже работающую поставку, а не исправляет её.

### Вне первой итерации

Windows, HTTP MCP, собственный updater, плагины, собственный MTProto, расширение набора инструментов и прав secretary. Импорт сессии не включается автоматически: его объём зависит от решения этапа 0.
